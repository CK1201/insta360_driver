# GO 3S Android 桥接采集

通过 **GO 3S → Wi-Fi → Android 手机 → USB/ADB → Ubuntu** 获取实时画面和相机传感器数据。手机运行精简桥接 App，电脑使用 YAML 设置曝光和白平衡，显示画面与六轴数据，并按需保存视频、时间戳和设备状态。

构建、APK 安装、连接及运行步骤统一见 [commands.md](commands.md)。配置见 [config/go3s.yaml](config/go3s.yaml)，传输协议见 [protocol/wire.md](protocol/wire.md)，版本记录见 [CHANGELOG.md](CHANGELOG.md)。

## 环境与边界

- 手机：Android 9/API 28 以上、ARM64。目标手机为小米 6，已通过 ADB 核对为 MI 6 / Android 9 / ARM64。
- 相机：GO 3S，通过 Wi-Fi 连接手机；电脑端的 USB 线连接手机，不直接使用 GO 3S 自身的 ADB 接口。
- Android：Camera SDK 2.2.6，APK 最低 API 28，只使用相机 SDK 及其必要依赖，不使用 Media SDK、手机摄像头或手机 IMU，不在手机上解码视频。
- Ubuntu：C++17、CMake、yaml-cpp、nlohmann JSON、FFmpeg、OpenCV、ADB。Android 构建另需 JDK 17 以上，工具链下载到项目 `.local/`。
- 首版使用普通视频模式的 SDK 原生预览，目标 30 fps，SDK 请求预览可能为 640×480 或 640×360，实机解码尺寸另行记录。录制分辨率不等于预览传输分辨率；不扫描其他帧率、不启动相机内部录像或 RTMP 推流。

采样率、时间单位、轴方向和物理量纲必须按实测报告解释，不预先套用 X5 的约 500 Hz 或标定参数。`CameraPosture` 方向枚举不能替代原始六轴数据。

## 使用方式与配置

手机先连接 GO 3S 热点并打开桥接 App，随后电脑启动 `insta360_go3s_client`。配置只在启动时生效，不支持热更新或自动重连。

| 配置 | 默认与含义 |
|---|---|
| `bridge.adb_serial` | 空：必须唯一找到已授权的 Android 9+ ARM64 手机；排除 Insta360/GO 相机自身的 ADB 设备 |
| `bridge.port` | 18765，电脑本地转发端口；手机服务固定监听 `127.0.0.1:18765` |
| `camera.serial` | 空：使用手机连接的 GO 3S；非空时核对序列号 |
| `camera.exposure.mode` | `auto`；另支持设备能力允许的 `manual`、`iso_priority`、`shutter_priority` |
| `iso` / `shutter_s` | 自动模式均为空；手动两项必填；两种优先模式只填对应项。快门单位为秒 |
| `camera.exposure.ev` | 常规 EV 数值，默认 0；不使用桌面 CameraSDK 的 EV×20 单位 |
| `camera.white_balance_kelvin` | 0 自动，否则设置设备支持的 Kelvin 值 |
| `stream.imu` | true，要求相机六轴数据持续到达；没有数据时不能判为有效传感器采集 |
| `preview.enabled` | true，电脑显示单镜头画面、最新六轴、请求/读回参数与实际速率 |
| `output.save` / `directory` | false / `../outputs`；路径相对于 YAML 所在目录，开启保存后每次创建独立目录 |
| `runtime.duration_s` / `status_interval_s` | 0 持续运行 / 1 秒状态报告（可设0.1–60秒）；命令行可覆盖时长 |
| `timing.sensor_delay_s` | 默认 0.0 秒；有限非负值，转换为整数纳秒后用于图像时间标签补偿 |

`--check-config` 只做本地配置校验，不调用 ADB、不访问相机或创建输出目录。实际启动会查询参数能力、下发并重新读取确认；相机不支持或读回不一致时明确停止，不自动替换请求。

电脑按 q/Esc、关闭窗口、Ctrl+C 或达到时长时请求手机停止预览并排空已接受数据，手机仍保持 GO 3S 的控制连接和前台服务，避免相机关闭 Wi-Fi；下一次电脑启动可直接复用该相机连接。断开电脑连接、序号缺口、队列溢出、写盘或解码失败会判为失败；曝光回调缺失单独告警。手机“断开相机”按钮才主动释放相机连接。真正的相机掉线会停止采集并报错，不自动重连相机。

## Python 帧接口

可选独立包 `insta360_go3s` 提供 `Reader(config="path.yaml")`、`Frame`。安装、运行和离线验证命令见 [commands.md](commands.md#8-python-安装与取帧)，完整示例见 [examples/read_frames.py](examples/read_frames.py)。默认 C++ CLI 构建不查找 Python 开发包或 pybind11。

构造只加载并校验 YAML，不查询 ADB、不访问设备或创建输出。`start()` 启动后台采集并返回自身；`with Reader(...)` 自动启动，退出自动停止。`stop()` / `close()` 可重复调用，结束后可再次 `start()`。Python 采集遵循原 YAML 的相机、保存和时长设置，强制关闭预览窗口，不读取 stdin，不安装进程信号处理器；不修改源配置文件。

| 接口 | 语义 |
|---|---|
| `latest(stream_index=0)` | 立即返回最新帧；无帧返回 `None`，并把当前 Reader 的消费游标推进到该帧 |
| `read(timeout=1.0, stream_index=0)` | 等待比消费游标新的帧；秒数必须有限且非负，`None` 无限等待；超时抛 `TimeoutError` |
| 正常结束 / 失败 | 正常结束且无新帧时 `read` 抛 `StopIteration`；后台失败后 `latest`、`read` 抛含原始原因的 `RuntimeError` |
| `running` / `error` | 采集后台是否仍在运行；错误字符串或 `None` |
| `Frame.image` | 独立、可写、连续的 NumPy `uint8` H×W×3 **BGR** 图像；每次交付复制像素 |
| `Frame.index` / `stream_index` | 每次会话从1递增；GO3S 只接受流0；重启清除帧、游标和错误 |
| `host_receive_ns` / `host_decode_ns` | 本机 `steady_clock` 纳秒：相关编码输入完整收到及帧解码完成时间，均不代表曝光时刻；无法关联接收时间时 `host_receive_ns=0` |
| `timestamp_ns` | `host_receive_ns - round(timing.sensor_delay_s × 1e9)`；收包时间未知时为 `0` |

每流只保留一个最新帧槽，慢消费者可能跳过序号，原始保存仍处理所有已接受数据。一个 Reader 共用一个消费游标，多线程不会各自获得独立帧队列。`latest` 也推进游标，因此随后 `read` 会等下一帧。已返回图像不会被后续帧或关闭修改，用户写入也不会污染缓存或其他已返回对象；接口不宣称零拷贝。视频不能可靠逐帧关联的设备时间戳继续保留在原始包索引，不在 `Frame` 中伪造设备曝光时间。

阻塞等待、启动和停止会释放 GIL，SDK/解码线程只运行 C++。停止会唤醒等待者并等待已接受原始数据排空；GO3S 手机前台服务、相机控制连接与心跳继续保留。不要让 Python Reader 与 CLI 同时独占同一手机桥接。

图像时间补偿与参考驱动的 [arrival − sensor_delay](https://github.com/specialist-ai/insta360_driver/blob/22641e241c18857f345fbbf8643592194beefb7f/python/insta360_driver/latency.py#L176) 同向：正值使时间向过去移动，默认 0 不补偿，省略该项也为 0。以电脑完整收包时刻为基准，补偿在图像产出时计算一次；CLI 保存和 Python `read/latest` 使用同一结果。它是主机单调时钟下的图像时间估计，不能当作已标定曝光时刻，不改变实际传输延迟。手机与相机的原始时钟及 IMU/曝光时间均不修改，该参数不发送给 Android SDK。

## 数据与时间

保存 SDK 提供的原始 H.264/H.265 字节、逐包偏移索引、原始 GYRO 字节及索引、六轴 CSV、曝光、状态、帧处理时间、配置副本、手机与相机信息以及结束摘要。电脑只在预览窗口缩放和叠加文字，不重编码采集视频。

| 文件 | 内容 |
|---|---|
| `video.h264` / `video.h265`、`video_packets.csv` | 原始编码视频与每包偏移、长度和三类时间戳 |
| `gyro.bin`、`gyro_packets.csv`、`imu.csv` | 原始 GYRO 批次、索引及相机六轴原值 |
| `exposure.csv`、`status.csv` | 实时曝光秒数与设备状态原始字段 |
| `frame_timing.csv` | 电脑接收与解码完成时间、实际帧尺寸；末列 `timestamp_ns` 为补偿后的图像估计时间 |
| `phone.yaml`、`session.yaml`、配置副本 | 手机/相机身份、SDK、请求与读回、有效配置 |
| `summary.yaml` | complete、退出与错误、数据计数、原始字节数量及 SDK 内部丢包未验证标记 |

重复开启预览时，相机可能先返回缺少初始化头的缓存 P 帧。它们仍完整保存，预览从首个可初始化关键帧开始，跳过数量记录为 `startup_units_skipped_for_preview`。外部解码器可能对这个前缀输出 PPS 告警；不要为此覆盖或裁剪原始录像。

每条记录区分相机原始时间戳、手机回调接收时间与电脑接收时间。手机与电脑的单调时钟属于不同域，不能直接相减当作网络时延或曝光时刻。电脑上的解码耗时只衡量电脑收到数据后的处理。

手机只在每次采集期间打开预览；电脑正常结束或 USB 断开后，保留相机 SDK 的控制连接和心跳。手机监听端可顺序接受后续电脑采集，每次使用独立序号，不同时运行多台电脑客户端。

手机、电脑均使用有界队列；回调只复制入队，由工作线程传输、保存和解码。桥接序号用于发现应用传输阶段的缺口。Camera SDK 内部存在未对外提供完整丢包计数的分发队列，因此 `sdk_internal_loss_observable: false` 会明确记录；桥接序号连续不证明 SDK 内部或传感器侧绝对无丢失。

## 结构与验证

| 位置 | 职责 |
|---|---|
| `android/` | 精简 Android App、前台服务、SDK 参数控制与转发 |
| `src/` / `include/` | 电脑 CLI、可选 Python Reader、ADB 选择与转发、协议、解码、保存和预览 |
| `scripts/` | 本地 Android 工具链与 APK 构建 |
| `tests/` | 配置、真实编码流、传输分块、失败和数据保存的离线验证 |
| `config/` / `protocol/` | 示例配置与两端共享协议 |

SDK 仓库访问配置从用户提供的原始 ZIP 读取，写入被忽略的本地文件，不放入源码、文档或输出日志。SDK 版本固定为 2.2.6，原始 SDK 的许可不由本项目重新授予。

构建、离线验证、真机采集分别记录。只有在真机持续收到画面和已启用的相机六轴数据、并核对完整文件后，才可以报告实机验收通过；不能使用模拟手机或手机自身传感器来替代。

## 本机验证记录

2026-11-17，v0.3.0 的 Python 接口已完成五组 CTest（含 15 项 Python 回归）和安装后 wheel 测试。另用真实 GO3S/小米 6 连续完成两次 Python 采集，实际图像均为 `640×384`；第二次 15 秒会话保存 388 帧、6400 条相机六轴样本、391 条曝光数据，首尾视频接收跨度 12.84 秒。视频完整解码、原始字节偏移与长度、CSV 计数和接受/处理事件数已核对。前台服务及相机连接复用，未重装或重启 Android 桥接。图像独立性、消费跳帧与正常结束已验证；这些结果不代表曝光到 Python 的总延迟或 SDK 内部绝无丢包。

已在小米 6（Android 9、ARM64）和 GO 3S 固件 v9.0.59 上完成自动及手动曝光采集，参数严格读回、视频和相机六轴/曝光均持续到达。目标20秒的两次运行，各自实际视频与IMU数据跨度均超过16秒，均正常stop/end。实际解码为640×384、视频约30fps，IMU时间戳中位步长2tick，结合设备时钟观察约500Hz；不将它视为物理单位、轴方向或硬同步标定。

| 场景 | 解码帧 | 相机六轴样本 | 曝光回调 |
|---|---:|---:|---:|
| 自动曝光、自动白平衡 | 489 | 8100 | 482 |
| 手动 ISO200、0.01秒、5000K | 489 | 8100 | 491 |

上述文件经过独立FFmpeg全解码、逐包偏移和全部六轴值与原始56字节记录逐条核对。桌面窗口已实际显示画面和数据。Camera SDK 的初始预览声明为640×360，实际状态与解码返回640×384，程序保留原始尺寸，不猜测裁剪位置。这是v0.1通用解码路径的历史验收；v0.2的低延迟改进见下文，主机处理耗时始终不是曝光到屏幕延迟。

电脑端4组离线测试与Android端11项单元测试通过；合成测试与上述实机结果分别记录在本机被忽略的构建/验收目录，原始采集数据保留在outputs。


持久连接版本还验证了连续两次电脑采集：第一轮513帧/8500条相机IMU，第二轮493帧/8250条相机IMU，均完整stop/end且数据跨度超过16秒。两次之间没有操作手机“连接”，前台相机服务身份不变、没有新建或关闭原生相机socket，电脑结束后继续等待下一次采集。第二轮先收到7个缓存P帧：500个原始视频包全部保存，预览从初始化头开始解码493帧；文件索引与跳过计数已独立核对。


## 低延迟预览（v0.2.0）

GO 3S 实采 H.264 为 I/P-only，每次 SDK 视频回调与独立解析的完整 access unit 边界一致，但 SPS 声明4帧重排。原通用路径还会等待下一帧来确定解析边界，离线回放共等待5帧。

电脑端现在直接提交已验证的完整 H.264 回调包，并只在解码器输入副本中将 SPS 重排声明设为0，沿用单线程解码、色彩处理和启动关键帧保护。原始录像、GYRO、IMU、曝光及各类时间戳不修改。H.265和分片字节流的C++解码接口仍使用通用parser；完整H.264快路径遇到B帧或不符合输入合同的数据会明确失败，不能静默丢弃原始数据或改变帧顺序。

真实GO3S录像按513个原始回调包回放，等待从5帧降为0帧，全部513帧BGR像素及主机接收时间戳完全一致。四组电脑端测试覆盖该路径、B帧拒绝、旧P帧启动、原始字节不变及解码错误后的队列排空。

同一组手动参数（ISO1000、0.0025秒、4600K）、保存开启、预览关闭的两次20秒目标实机测试：

| 电脑收包到解码就绪 | 原路径 | 低延迟路径 |
|---|---:|---:|
| 平均 | 166.92ms | 1.03ms |
| 中位数 | 188.95ms | 0.79ms |
| P95 | 195.60ms | 1.59ms |

两次均完整stop/end，分别527/519帧、8700/8600条相机IMU，参数读回一致；录制文件SPS仍为原始reorder=4，全视频独立解码、逐包索引和所有六轴原值检查通过。`summary.yaml`新增`preview_decode_mode`、`preview_sps_patches`说明实际解码路径和副本修改次数。数字包含电脑排队与处理等待，不包含相机编码、Wi-Fi、手机SDK、USB传输或显示器发光延迟，也不等于CPU纯解码计算时间。

低延迟helper通过现有X5实现参考固定版本上游，第三方来源和MIT许可见 [说明](third_party/insta360_driver/README.md)。本轮只更新电脑端，不需要重装手机App，采集结束继续保持GO3S控制连接。当前YAML以你的编辑值为准，省略字段时才使用表中的默认值。
